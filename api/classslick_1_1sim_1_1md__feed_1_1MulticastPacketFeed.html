Detailed Description

The transport half of a live multicast feed: one receiver thread per joined group ("line"), all handing their packets to the exchange thread through one lock-free queue.

Nothing here takes a lock. Only the exchange thread touches the book, as it drains the queue into the venue's protocol handler.

A line is a small integer below MAX_LINES that the venue chooses (its enum). The venue can mute a line it has no use for, such as a snapshot loop while the book is live, and its packets are then dropped on arrival. The receiver stays joined, because leaving and rejoining a group takes longer than a gap may last.

Header-only, so the md_feed target stays free of slick-socket: a venue that includes this links slick::socket itself.

Config keys, read from the feed's config entry: queue_size (bytes, default 16 MiB), max_packets_per_poll (256), interface and receive_buffer_size for every receiver. Each line's group is { "address", "port" } under its key.

The queue is fixed and lossy, like every slick::queue: should the exchange thread fall far enough behind, a receiver overwrites packets nobody has drained, and loss_count() counts their bytes. The venue's own sequence numbers are what turn that into a gap it can recover from. A packet is also held back from the queue until the receiver that reserved its slot has copied it in, so one stalled copy delays the packets behind it - never reorders them.

Queues a packet as if line's receiver had received it.

Any thread. False when the packet is dropped: the line is muted, or the packet cannot fit the queue.

The second case has to be refused here. slick::queue::reserve() throws above the queue's size, and this runs on a receiver thread, where an escaping exception is std::terminate - a queue_size smaller than one datagram would otherwise take the process down.
